# 本番D1とmigrationの照合結果

実施日: 2026-08-21  
対象: Cloudflare D1 `line-harness`（本番）  
実施内容: 読み取りのみ。この照合では本番へ一切書き込んでいない。

## なぜ照合が必要だったか

`.github/workflows/deploy-cloudflare-worker.yml` は、`_migrations` テーブルに
記録が無いmigrationを「未適用」とみなして本番へ流す。しかし本番D1に
`_migrations` テーブルは**存在しない**（`sqlite_master` で確認済み。
似た名前の `account_migrations` は無関係な機能テーブル）。

このまま自動deployを有効化すると、76件すべてを未適用とみなして再実行する。
その中には次のような破壊的な操作が含まれる。

- `027_dedup_delivery.sql`: `DELETE` → 表の作り直し → `DROP TABLE friend_scenarios`
- `029_account_management_v2.sql`: 表の作り直し → `DROP TABLE broadcasts`

途中で失敗すると「消したのに作り直せていない」状態になり得るため、
**自動deployを有効化する前に `_migrations` を正しい状態にする必要がある。**

なお「76件すべてを一律で適用済みとして登録する」のは誤り。本当に未適用の
変更まで永久に飛ばしてしまうため、1件ずつ照合した上で判断する。

## 照合方法

正規表現による突き合わせは取りこぼしが出たため、決定的な方法を採用した。

1. ローカルの空SQLiteに `packages/db/schema.sql` を適用（土台）
2. その上に `packages/db/migrations/*.sql` 76件を番号順に適用
3. 出来上がった「あるべきスキーマ」を取得
4. 本番の `sqlite_master` を取得し、同じ手順でローカル再現
5. テーブル / 列 / インデックスを全件比較

再現スクリプトの考え方はこのドキュメントに記載のとおり。実行時は
必ず本番のバックアップを先に取得すること。

| migration | 内容 | 本番の状態 |
| --- | --- | --- |
| `026_delivery_type_test.sql` | `SELECT 1;` のみ（無効化済み） | 実行しても何も起きない |
| `037_scenario_delivery_mode.sql` | `SELECT 1;` のみ（無効化済み） | 実行しても何も起きない |

| `062` / `063` / `065` / `066` | マイル機能の初期ルールを投入 | **未反映**（`mileage_rules` が0件） |

### マイル機能の初期ルールについて

`062` `063` `065` `066` は構造変更こそ反映済みだが、`mileage_rules` への
初期データだけが入っていない。現在 `mileage_rules` は0件。

これらのルールは `is_active = 1` で投入されるため、そのまま適用すると
「メッセージ受信」「リンククリック」「フォーム送信」「予約作成」などを
きっかけに、友だちへ自動的にマイルが付与され始める。

現在のFrei / WAHMSの運用ではマイル機能を使っていない（`mileage_ledger` 0件、
`webinars` 0件）。したがって**適用するかどうかは技術判断ではなく事業判断**であり、
運用者の明示的な決定が必要。

なお「この4件だけ `_migrations` に記録せず保留する」という選択はできない。

- `062` / `063` は `ALTER TABLE ADD COLUMN` を含まないため、再実行すると
  初期ルールが投入され、マイル付与が実際に始まってしまう。
- `065` / `066` は `ALTER TABLE ADD COLUMN` を含む。列は既に存在するため
  再実行は `duplicate column name` で失敗し、deploy自体が止まる。

つまり選択肢は次の2つに限られる。

1. 4件とも「適用済み」として記録し、マイル機能は休止のまま据え置く。
   将来必要になったら、投入部分だけを新しいmigration（077以降）として
   レビューの上で追加する。
2. 4件のINSERT部分だけを意図的に手で適用し、マイル付与を開始した上で記録する。

現状の運用実態からは 1 を推奨する。

### 参考: 現状の注意点

`067` が投入した「マイル」キーワード自動応答は `line_account_id` が NULL の
ため、**全LINEアカウント共通で有効**になっている。マイル規則が0件のため
残高は常に0として返る。運用意図と合っているか、別途確認したほうがよい。

## `_migrations` の整備（2026-08-21 実施済み）

運用判断は前節の選択肢 **1（マイル機能は休止のまま据え置き）**。
これを踏まえ、次の手順で実施した。

1. 直前に本番D1のフルバックアップを取得（リポジトリ外に保管）
2. `_migrations` が未作成であることを再確認
3. `CREATE TABLE IF NOT EXISTS _migrations` と `INSERT` 76件のみのSQLを生成し、
   `DELETE` / `DROP` / `UPDATE` / `ALTER` が含まれないことを確認してから実行
4. 記録された76件が `packages/db/migrations/*.sql` と完全一致することを検証
5. deploy workflow と同じ判定コマンドで、破壊的な `027` `029` を含む
   代表migrationが「適用済み」と判定されることを実地で確認

実施後の確認結果:

| 確認項目 | 結果 |
| --- | --- |
| `_migrations` 記録件数 | 76（実ファイルと完全一致、過不足なし） |
| 既存データの変化 | なし |
| `mileage_rules` | 0件のまま（休止を維持） |
| Worker `/health` / 管理画面 / WAHMS管理 | いずれも 200 |

これにより、自動deployを有効化しても76件が再実行されなくなった。

### 今後マイル機能を使いたくなったら

`062` / `063` / `065` / `066` のINSERT部分を再利用し、**新しいmigration
（077以降）としてレビューの上で追加する**。既存migrationの `_migrations`
記録を消して再実行してはいけない（`065` / `066` は列重複で失敗する）。
